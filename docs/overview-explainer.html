1. Where cost decides, and where readiness overrides it

When a ReplicaSet scales down, the controller compares pods step by step (ActivePodsWithRanks.Less, §6). The first step where two pods differ picks the victim. Later steps are never reached. pod-deletion-cost is step 4, so it only matters when steps 1 to 3 tie.

This is why queue consumers should report accepting: false to Knarr rather than go NotReady while busy (§5). Even when cost is reached, the result is best-effort: the controller reads pods from its informer cache, which may not yet hold Knarr's latest patch (§6).

2. From worker cost to annotation value

Knarr writes the worker's cost itself, clamped to int32, when the cost crosses a configured threshold (§4, §6). Below the first threshold the pod is idle and carries no annotation; a draining pod below the first threshold is -1, entered and left on the reading that says so, with no margin. Between crossings the applied value stands. A margin below each threshold damps the way down. Settled in docs/specs/cost_mapping.allium (§9.5).

Where the values sit relative to the implicit 0

Pods with no annotation count as 0, and lower cost is deleted first. Knarr's convention puts idle, a cost below the first threshold, at 0, so Ready pods that Knarr has not annotated yet tie with idle pods; busy pods carry their cost and are protected over both; a draining pod below the first threshold is -1 and goes first (§6).

The same choice fixes the neutral fallback value (§9.6) and what removing an annotation means (§9.12): both are the removed annotation, the same as idle. No values are reserved for Knarr's own states.

3. Which levers work on which kill path

Knarr's two levers each cover only part of the picture (§2). Graceful drain in the worker is the one protection on every path, and only where a grace period is given.
