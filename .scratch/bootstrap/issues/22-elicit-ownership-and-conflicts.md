# 22: Elicit: ownership marker, write mode and conflicts (§9.10)

**Context:** OVERVIEW §8 proposes a knarr marker annotation that holds the last-written value and a timestamp. §9.10 leaves open:

- the marker's design
- the write mode: an unconditional merge patch, a `resourceVersion` precondition, or a JSON Patch `test`
- emitting an Event and backing off when another writer changes the value
- the LIST-to-PATCH window: S1's probe decides `NoPatchWhileTerminating` from the last LIST and patches unconditionally, so a `deletionTimestamp` set between the two is not seen. A `resourceVersion` precondition or a JSON Patch `test` is what closes it (raised in the review of pull request #15)

Other writers include user-set values, the lablabs and zepellin controllers, and Karpenter with `PodDeletionCostManagement` enabled. The goal is that the other writer wins.

**What to build:** Allium clauses for ownership and conflict handling, settled with the maintainer, that the patcher and the cleanup rules (23) can rely on.

**Non-goals:** Freshness and restart semantics (23). Rate limits (24).

**Blocked by:** 17

**MVP critical path:** yes. Every patch knarr writes depends on the marker and the write mode.

**Status:** done. See [the hand-back notes](#hand-back-notes).

### Choices a maintainer may reverse

- The view a patch and a standing are built from is the newest API-returned state knarr holds for the pod: the last LIST or its own last accepted patch response, later by the order the responses were received. Without this a second due write before the next LIST (a crossing then an `accepting` toggle) would test against a marker its own first patch changed and 422 every time. This is API state, not the in-memory counters §8 forbids.
- `standing` is defined for both owned annotations whatever the Deployment enables; reconcile asks it for a disabled annotation only while the marker holds a record for it, so an opt-out's leftover value falls to cleanup (23) under the opt-out gate (25), and `safe-to-evict` on a Deployment that never opted in is never asked about and raises no log line.
- A hand edit of the marker is detected as the raw string differing from `render` of what `read` reads, which refines Settled row 10: an edit that breaks the canonical form or the shape reads as no marker, while an edit that keeps the canonical form reads as what it says, so a changed applied value surfaces as a conflict and is yielded rather than parked as foreign. A future change of the canonical form reads every older marker as unusable, foreign while the annotation is present and adoptable while absent, until it is rewritten. The alternative was to treat every edit alike, which `read` cannot detect for one that keeps the form.
- Each record carries its own `at` and the marker a top-level `at` for the last write to the pod. A member of any other name makes the marker unusable, so a rollback to an older knarr after a newer one recorded a third annotation reads that pod's marker as no marker, foreign while an annotation is present and adoptable while absent, until the older binary rewrites it; the alternative, carrying an unknown member through `render`, would have to reconcile with the edit detection above.
- The Event is built from the marker and annotations the yield patch was built from, so `applied` is the record the yield replaced, and it is raised after the yield patch is accepted, never before. A crash between the accepted yield patch and the Event create loses that pod's Event for good, because the record is already on the pod and nothing repeats while yielded; the ordering was chosen so that no Event is raised for a yield that did not land.
- Every patch on a live pod tests `/metadata/deletionTimestamp` against null, and on a live pod that field is absent, as is a never-written owned annotation. The write mode rests on the apiserver's JSON Patch library treating a missing key as equal to null; 41's kind check proves it before anything is built on it.
- `patch` and `yield` return `List<Operation>` and `document` owns the encoding to the JSON Patch body; `remove` carries no value and a `test` for absence carries the JSON text `null`.
- `may_write`, `document` and `message` give `Standing`, `Operation` and `ConflictEvent` a parameter position, since the pinned checker flags a value type used only as a bare return.
- The shape invariant is named `Recorded`, not `Marker`, to keep clear of `value Marker`.
- `ownership` declares its own `Annotation`, as `knarr` and `worker_contract` each declare `Request`, `Header` and `Response`; the pinned checker accepts the duplicate across modules.
- No decision record; the module header, OVERVIEW and this ticket are the record, and Decision 0013 carries inline amendments.
- 32 and 41 are amended rather than a new ticket drafted.

### What later tickets need

- **19:** the marker key is `knarr.io/applied`: the prefix you settle plus `applied`, with `knarr.io` standing in until then (ownership `Recorded`). Nothing in ownership is overridable. If the prefix is configurable, the marker key becomes a parameter of `read`, `patch`, `yield` and `render`, since `Pure` forbids them reading config, and the obligation count moves.
- **23:** cleanup removes the annotations standing owned; a yielded or foreign value stays. `standing` is defined for both owned annotations, and reconcile asks it for a disabled one only while the marker holds a record for it, so an opt-out's leftover value falls to your cleanup under 25's opt-out gate. Whether the marker goes with the last owned annotation is yours: `Applied` keeps it on the idle removal. The operator releases a yield by removing the marker together with every owned annotation on the pod (Settled row 10), since removing the marker alone leaves every present value foreign; the procedure is your uninstall and manual recovery, and its page is 34's. The marker's `at` and each record's `at` are the write times whose meaning over time is yours, and a `Pod` may have no annotations map at all.
- **24:** a yield patch is a write like any other and counts against the budget, and a write and a yield on one pod in one cycle are two writes against it; a foreign annotation costs no write. A 422 makes no retry in its cycle, so it adds no write before the next LIST.
- **25:** `safe-to-evict` is an owned annotation under `Adoption`, `Applied` and `Yield`; `standing` is defined for it whatever the Deployment enables, and reconcile asks it on a Deployment that has not opted in only while the marker holds a record for it, so an opt-out's leftover falls to cleanup (23); the opt-in and opt-out gates are yours; its yield is independent of `pod-deletion-cost`'s.
- **30:** the conflict Event's content and message are fixed by `Event`, one per yield, on the Pod, after the yield patch is accepted; you name its reason. Name also the gauge and the log line `Adoption` requires for a foreign annotation, which raises no Event, and settle the log line's cadence: on each LIST that shows the value, or on entry.
- **31:** ask `standing` and `may_write` before a patch and pass `patch` only the due writes it allows, since a forbidden write and a null write on an absent annotation are dropped; yield with `yield` on a conflict, and build the Event from the pre-yield marker and annotations, sending it only after the yield patch is accepted; parse the applied record to `Mapped` and to `safe-to-evict`'s value, and yield a record that does not parse. A 422 waits for the next LIST, with no GET and no retry: keep the failed patch's operations until then and classify with `rejected`; a restart forgets them.
- **32:** build the `Ownership` contract with the tests your box lists; a 422 is classified by the next LIST with `rejected`, and the decided rejected-patch row applies only once `rejected` is true for that LIST's view.
