# 19: Elicit: label and annotation configuration schema (§9.1)

**Context:** OVERVIEW §9.1 decides that knarr is a controller configured through labels and annotations on Deployments, installed in one namespace with a Role (§9.18). The schema was open: how a Deployment opts in, how it overrides the endpoint or tuning, how it opts into `safe-to-evict`, and how knarr refuses or warns when pointed at StatefulSets, Jobs or DaemonSets (§3 non-goals, settled as documented rather than detected).

**What to build:** Allium clauses for the configuration schema, settled with the maintainer: every label and annotation knarr reads, its type, default, validation, and the behaviour on invalid values. Some overrides take values another elicitation ticket owns: the endpoint (18), the thresholds and margin (20), unreachable windows (21), staleness and expiry (23), and poll and write limits (24). For those, the default and valid range come from the owning ticket. If it is not done yet, they stay as open questions that ticket owns.

**Non-goals:** The values of the tuning defaults themselves (18, 20, 21, 23, 24). The `safe-to-evict` policy (25).

**Blocked by:** 17

**From 24:** two overrides: `poll_interval` (whole seconds, 5 to 300, default 30, valid only when greater than the install-wide `poll_timeout` as configured, 5 s by default and up to below the install-wide poll interval, else an invalid value under this ticket's rule) and `patch_interval` (whole seconds, 0 to 3600, default 60; 0 is valid and leaves the global bucket as the only bound on that Deployment's pods, after a rejection too, with no floor applied). The timeout has no override. The key syntax and the handling of an invalid value are this ticket's.

**From 30:** [observability.allium](../../../docs/specs/observability.allium) states the conventions any signal this ticket settles follows: metric names, labels and series life (`Catalogue` `Naming`, `Labels` and `SeriesLife`), Event reasons and type (`Events` `Conventions`), and log fields and levels (`Logs` `Format` and `Levels`). This ticket adds its own rows there with `tend` when it settles, without reopening 30 (`Catalogue` `LaterRows`). An invalid override, whatever this ticket decides it does, is such a row: its metric, Event or log line is named then. `config.log_level` (`Logs` `Levels`, default info) is install-wide, set by OTP application configuration as knarr's `Listening` sets the bind address; observability gives it no per-Deployment override. The `tier` label of `knarr_pods` ranges over `drained` and 0 to the length of a Deployment's effective threshold list, whose length this ticket's `Keys` does not cap, so its value count is a sizing assumption and not a limit knarr enforces (`Labels`).

**MVP critical path:** yes. Users configure the MVP through this schema.

**Status:** done. See [the hand-back notes](#hand-back-notes).

### Choices a maintainer may reverse

- `Discovery` matches the owner chain by uid, with the controller owner reference only, so a Deployment deleted and recreated under one name adopts no pod of the old one. Matching by name is one sentence to change.
- `Discovery` follows every ReplicaSet a Deployment controls, so a rollout's old and new pods are both targets (§9.13). Restricting to the newest ReplicaSet would be a rule here and a change to §9.13.
- `Effective` sets the margin to 0, not the default, when a thresholds override undercuts the effective margin; the alternative, refusing the thresholds override instead, was put to the maintainer and rejected (row 9).
- `InvalidValue` keys the Event's "on entry" to the invalid value text, so correcting a typo into a second typo raises a second Event; keying it to the key alone would raise one per episode.
- `Syntax` rejects a leading zero and a `+` sign, matching cost_mapping's canonical string, and a threshold above 2147483647, which cost_mapping's `Clamp` makes unreachable; accepting either is one sentence. The trim set is the four ASCII whitespace characters.
- `InvalidValue` keys its memory by Deployment uid and key and forgets the text once the key reads valid, is absent or the Deployment leaves the target set, so a typo repeated after a fix raises again. `unknown` returns each key prefixed by `label` or `annotation` so the log line names the map.
- `Discovery` has `targets` re-apply `opted_in` to each listed Deployment, so the selector is never the rule, and defines the pods budget schedules as the target set rather than the raw pod LIST.
- `Unknown` reports a key under the prefix only; a key under another prefix is not knarr's. Reporting `knarr.io/applied` on a Deployment, where it has no meaning, falls under `Unknown` as written.
- `leaving` sits here because the target set is config's and names only pods the cycle's pod LIST still shows; it could move to lifecycle when 23 drafts cleanup.
- The `Pod`, `ReplicaSet` and `Deployment` values carry only what discovery reads; 41 shapes the client's values and may merge them with k8s_client's `Pod`.
- Decision 0009's rows keep their 2026-10-08 class, as 18's, 20's, 22's and 24's do.
