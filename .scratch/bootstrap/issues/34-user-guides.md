**From 21:** the operations page content from [21's Settled table](21-elicit-unknown-unreachable-policy.md#settled) and [reconcile.allium](../../../docs/specs/reconcile.allium): the two windows, `unknown_polls` (default 3, valid 1 to 100) and `absent_after` (default 300 s, valid 30 to 3600 s), install-wide with no override; that after three consecutive readings that are not valid every Knarr-owned annotation is removed; that 404 or refused for 300 s raises `ContractAbsent` on the Deployment with the effective port and path and shows on `knarr_pods_contract_absent`, that polling continues and the pod is managed again from its next valid reading; `knarr_pods_unknown` for the pods whose window has elapsed; that a NetworkPolicy block looks like a timeout, raises no Event and shows on `knarr_polls_total{reading="timed_out"}`; and that a restart keeps values until the window elapses again.

**From 24:** the `PodDeletionCost` prerequisite page content, row 14 of [ticket 24](24-elicit-poll-budget-feature-gate.md#settled): the gate is beta and on by default since Kubernetes 1.22, and is needed on both kube-apiserver and kube-controller-manager; GKE enables beta gates by default, may disable one per version, and allows gate changes only on alpha clusters; knarr makes no check. The verification is `kubectl get --raw /metrics | grep 'kubernetes_feature_enabled{name="PodDeletionCost"'` on 1.26 or later, which proves only the apiserver's gate. The behavioural test uses two Ready pods of one Deployment on the same node (or on nodes with equal counts of its pods): annotate the older with `controller.kubernetes.io/pod-deletion-cost: "-1"` and scale down by one; with the gate on the older goes, and with it off the newer goes, since ranking then prefers the pod that became Ready more recently. With the gate off knarr's writes are harmless and useless, and `safe-to-evict` and Karpenter are unaffected. The page cites the kubernetes.io feature-gates reference, the ReplicaSet page's pod-deletion-cost section, KEP-2255 and the GKE feature-gates page.

**From 23:** the uninstall page content from [23's Settled table](23-elicit-cleanup-staleness-restart.md#settled) and lifecycle `Uninstall` `Procedure` and `Recovery` in [lifecycle.allium](../../../docs/specs/lifecycle.allium): uninstall is opt every Deployment out, wait for cleanup, delete knarr. The operator removes `knarr.io/enabled` from every opted-in Deployment; waits until `knarr_annotations{standing="owned"}` is 0 for the install or absent, since a Deployment's series are removed once its cleanup is done; then removes any marker left, whatever left it (a yield or a conflict leaves one since neither is ever cleaned up, and a marker-only cleanup may still be pending), which `kubectl get pods -o jsonpath` over `knarr.io/applied` lists, an unusable or edited marker included, with the full release command `kubectl annotate pod <p> knarr.io/applied- controller.kubernetes.io/pod-deletion-cost- cluster-autoscaler.kubernetes.io/safe-to-evict-`; then deletes the install with `kubectl delete -k`. Deleting knarr before the wait leaves every owned annotation as a leftover. A value of an owned key on a pod with no marker is foreign and the procedure leaves it, since it may be another writer's; an operator who removed a marker by hand without its annotations finds such values with a `kubectl get pods -o jsonpath` over the two owned keys and removes them one key at a time. Manual recovery after a dead install, or for a pod a permanent rejection leaves annotated, is the same per-pod command, with the caveat that it also removes a value another writer owns, so on a pod a `CleanupRejected` message shows to carry one the operator removes knarr's keys one at a time as that message renders them; removing the marker alone leaves every present value foreign. The operations guide also says, from lifecycle `Restart`, that a restarted knarr makes no startup pass and reconciles marked pods through the normal loop, that no annotation expires by age, that the reading window is the only expiry, so a found value stands until the window elapses again or the first valid reading corrects it, and that the marker's `at` and each record's `at` are informational, deciding nothing in knarr; and, from lifecycle `Cleanup` `Scope` and `Order`, that a Deployment's opt-out removes knarr's annotations from its live pods from the next discovery cycle, oldest-due first within the write budget (the two list intervals of `Restart` `Threshold` (b) are the harness threshold after a restart, not a guarantee).

**From 37:** the install as [37's hand-back](37-first-release-v0-1-0.md#what-each-later-ticket-needs) settled it. At a release's own tag `deploy/release` still holds the previous digest, because the pin lands on `main` only after the run has pushed. An install checks out the tag, runs `just release-pin <digest from the run>` there, which pins only the local copy and checks the render, then applies `deploy/release` with `kubectl apply -k` ([install-at-tag.txt](../evidence/37/install-at-tag.txt)). `just release-pin` takes the bare `sha256:` digest, the run log's `digest=` line or the part after `@` in the reference the run summary prints, and needs the cluster environment (`just cluster-install`). `pin-digest.sh` checks the render with that environment's kustomize, and `kubectl apply -k` applies with kubectl's bundled one; they render the same pinned image, and the guide names both. The package is public, so the overlay needs no `imagePullSecrets`. 0.1.0's digest, `sha256:97262e02b6326b73ac414fa1bb01b6f557b1c352b7d647a30d7835e4a59e22c7`, is a worked example; 40's hand-back records the MVP's.
