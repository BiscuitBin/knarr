# 23: Elicit: cleanup, staleness, restart and uninstall (§9.12)

**Context:** OVERVIEW §9.12 offers three cleanup options:

- (i) never clean up
- (ii) clean up when a pod or workload leaves scope
- (iii) also clean up on graceful shutdown

It also covers:

- separate expiry for deletion cost and for `safe-to-evict`
- what the marker timestamp means
- conservative behaviour on restart when freshness is unknown
- startup reconciliation of marked pods
- annotations left after a crash
- an uninstall procedure

§8 names the open tension: writes are sparse, so a last-written timestamp cannot tell a steady cost from hours of failed polls. A §3 success criterion requires that a restart does not make annotations flap.

Ticket 22 settled the marker in [ownership.allium](../../../docs/specs/ownership.allium) and hands this over. Cleanup removes the annotations standing owned; a yielded or foreign value stays. `standing` is defined for both owned annotations whatever the Deployment enables, and reconcile asks it for one the Deployment no longer enables only while the marker holds a record for it, so the value an opt-out leaves behind falls to cleanup here; the opt-in key and its parse are config's `SafeToEvict` (19) and the gate's behaviour is 25's. Whether the marker goes with the last owned annotation is yours to settle, since ownership's `Applied` keeps it on the idle removal. The operator releases a yield by removing the marker together with every owned annotation on the pod ([22's Settled row 10](22-elicit-ownership-and-conflicts.md#settled)); removing the marker alone leaves every present value foreign, and the procedure page is 34's. The marker's `at` and each record's `at` are the write times whose meaning this ticket settles, and a `Pod` may carry no annotations map at all (`Pod.annotations` null).

**From 19:** config's `leaving` returns the names of the pods a Deployment's opt-out (label removed or changed) or deletion dropped from the target set at a discovery cycle; what is left on them is this ticket's. [config.allium](../../../docs/specs/config.allium) leaves one open question for this ticket: whether a staleness or expiry value gains a per-Deployment override, under the same key, syntax and invalid-value rules as every override there; close it either way.

**From 21:** the reading windows [reconcile.allium](../../../docs/specs/reconcile.allium) settles are in memory (reconcile `Window`, `Absent` and `Restart`), so a restart keeps a found value until the window elapses again in the new process; the marker's `at` and each record's `at` are yours to give meaning across a downtime, and lifecycle's expiry question is now of a value a restarted knarr finds on a marked pod. The neutral write for lack of data has purpose `apply` and keeps the pod managed (reconcile `Neutral`), so purpose `cleanup` is yours alone, for a pod or annotation leaving knarr's management; what an absent pod's leftover means after a downtime is yours. The Expiry, Marker freshness and Restart open questions in [lifecycle.allium](../../../docs/specs/lifecycle.allium) say so. The neutral write may pre-empt a cleanup: a safe-to-evict value an opt-out left is removed with purpose `apply` if the pod goes neutral before your cleanup reaches it (reconcile `Neutral`).

**What to build:** Allium clauses for cleanup, staleness, restart and uninstall, settled with the maintainer, consistent with the sign convention (20) and the marker (22).

**Non-goals:** The `safe-to-evict` threshold itself (25).

**Blocked by:** 20, 22

**From 30:** [observability.allium](../../../docs/specs/observability.allium) states the conventions any signal this ticket settles follows: metric names, labels and series life (`Catalogue` `Naming`, `Labels` and `SeriesLife`), Event reasons and type (`Events` `Conventions`), and log fields and levels (`Logs` `Format` and `Levels`). This ticket adds its own rows there with `tend` when it settles, without reopening 30 (`Catalogue` `LaterRows`). Already fixed: a removal knarr makes because a pod or an annotation leaves its management has purpose `cleanup` on `knarr_patches_total` and `knarr_patch_rejections_total`, and a rejected cleanup raises `CleanupRejected` on the Pod on the first rejection of a run, with a message naming each annotation left and the `kubectl annotate pod <pod> <key>-` that removes it (`Events` `CleanupRejected`). What counts as a cleanup is this ticket's. A Deployment's series retire only once it has left the target set and nothing for its pods is pending, in flight or awaiting cleanup, so when a Deployment's cleanup is done, which is this ticket's, is when its series go (`SeriesLife`). A restart starts every counter at 0 and rebuilds the per-Deployment gauges from the first discovery cycle in which every LIST of it succeeds (`SeriesLife`).

**MVP critical path:** yes. Restart safety is an MVP success criterion.

### Choices a maintainer may reverse

- Rejected cleanup is memoryless: due again at the next cycle, no sooner than the patch interval (budget `PerPod`), while the pod lives, is not terminating and stays out of scope. `CleanupRejected` once per run (observability `Events` `Rejected`). A permanent webhook rejection keeps the Deployment's series alive at one attempt per pod per interval; the Event and `knarr_patch_rejections_total{purpose="cleanup"}` show it.
- Conflict or foreign on a leaving pod: left as found, no yield, no Event; a conflict's record stays, and a later re-opt-in sees the conflict and yields then. A marker that is absent, unusable or edited holds nothing, so nothing is due, and a value on a pod with no marker is foreign, which the uninstall procedure leaves too (lifecycle `Uninstall` `Procedure`).
- Terminating pod: no cleanup is sent (k8s_client `NoPatchWhileTerminating`) and none is awaited; it does not hold a Deployment's series (`due` returns nothing for it).
- Re-opt-in with a cleanup in flight: the accepted cleanup's response is the newest view; the next cycle finds a target with no marker, unowned and adoptable, rewritten at its first valid reading at or above the first threshold. One extra write.
- One pod due both an apply and a cleanup: two patches, each with its own purpose, served oldest-due first under budget `order`; the second waits the patch interval. budget's `Pending` gained `purpose: apply | cleanup` for this (the count is unchanged since a value type counts two whatever its fields).
- The per-pod interval of a cleanup on a non-target pod is `config.patch_interval`: the Deployment's override cannot be read because the opted-out Deployment is not in the selected LIST.
- A neutral removal (reconcile `Neutral`, purpose apply) of a disabled safe-to-evict leaves a null record that stands owned, so it is still due a marker-only cleanup; ownership `Released` builds that patch. One extra patch in a rare overlap; the alternative was to make the neutral write drop records, which mixes two purposes in one patch.
- `deployment` label for a non-target pod: the name the pod's ReplicaSet's controller owner reference carries (k8s_client `Owner.name`), since the opted-out Deployment is not in the selected LIST and config's `ReplicaSet` reads no name. A marked pod whose chain names no Deployment (cascade-orphan deletion) is still cleaned up, counted with `deployment` empty; those series live and retire under the empty name.
- When a Deployment's cleanup is done (observability `SeriesLife`): `done` is true when no live, non-terminating view of its pods has a non-empty `due` and no cleanup pending or in flight carries its name. Each `Removal` carries the `deployment` of the View that made it, so a cleanup in flight for a pod that has since left the LIST still holds the series. `done` is a signature so it is testable; `outstanding: List<Removal>` gives `Removal` a parameter position (the pinned checker flags a bare return).
- `Held` carries ownership's standing rather than the marker and annotations, so `due` does not restate `Adoption`; the caller builds it with ownership `read` and `standing`. lifecycle declares its own value types because no module imports another (Decision 0009).
- Crash leftovers and a down knarr: the restart rule is the whole answer; a leftover from a crash is a value the new process finds. While knarr is down nothing moves; `safe-to-evict: "false"` can pin nodes (§8 row, decided, 32). The recovery is the uninstall procedure's manual step.
- On a pod that is not a target, `knarr_annotations` counts only annotations standing owned (observability `Standing`), so a yielded or conflict record an opt-out leaves counts nowhere and the Deployment's series retire once `done`. The alternative was series that live while any listed pod with that name holds a record, for such a pod's life.
- A rejected marker-only cleanup that would have rewritten the marker, keeping other records, raises `CleanupRejected` with no command (observability `CleanupRejected`): removing the marker would leave the pod's other values foreign for its life. One that would have removed the marker still names `knarr.io/applied-`. The maintainer chose "no command on a pod still a target"; `RejectedEvent` carries whether the marker would have been rewritten or removed but not whether the pod is a target, so the clause keys it on that, which covers every case where removing the marker by hand does harm.
- Uninstall procedure (clauses in lifecycle `Uninstall`; the page is 34's): remove `knarr.io/enabled` from every Deployment; wait until `knarr_annotations{standing="owned"}` is 0 for the install or absent, since a Deployment's series go once its cleanup is done; remove any marker left, whatever left it (a yield or a conflict, or a marker-only cleanup still pending), which `kubectl get pods -o jsonpath` over `knarr.io/applied` lists, with the full release command (`kubectl annotate pod <p> knarr.io/applied- controller.kubernetes.io/pod-deletion-cost- cluster-autoscaler.kubernetes.io/safe-to-evict-`); then `kubectl delete -k`. Manual recovery after a dead install is the same per-pod command, with the caveat that it also removes a foreign value, so a pod another writer touches is done one key at a time as the `CleanupRejected` message shows.
