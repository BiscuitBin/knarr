# 47: Discovery's cleanup hand-off

**Context:** Ticket [23](23-elicit-cleanup-staleness-restart.md) settled `docs/specs/lifecycle.allium` after [31](31-spec-then-build-reconcile-core.md) had built the reconcile core, and its `From 23` paragraph in 31 gives 31's discovery process the work of building lifecycle's `View` for every listed pod and handing it to `Cleanup` `due`. That work calls the `Cleanup` contract and ownership's `cleanup`, which [32](32-spec-then-build-ownership-lifecycle.md) builds, and sends through the pending set [46](46-spec-then-build-poll-schedule-and-patcher.md) builds, so 31 merged without it; [31's hand-back](31-spec-then-build-reconcile-core.md#after-merging-main-ticket-23) lists what is missing. Until this lands nothing runs cleanup: the pods of a Deployment that opted out or was deleted keep knarr's annotations and marker, and a safe-to-evict whose opt-in was removed stays.

**What to build:** The wiring between the three LISTs and lifecycle's contracts, in the reconciler as 46 leaves it, test first in the order the `gleam-change` skill sets. No clause changes: lifecycle, ownership, budget and observability already state every behaviour below, and a gap found is a `spec-change`, not a judgement call in code.

**Non-goals:** `Cleanup` `due` and `done` and ownership's `cleanup`, which 32 builds. The pending set, the bucket, the per-pod interval and the pause, which 46 builds. The rejection signals and their cadence (`CleanupRejected`, `knarr_patch_rejections_total`), which 32 builds; this ticket feeds them a cleanup's outcome. Lifecycle's `Restart` and `Uninstall` beyond the first cycle below (32, 34). The pod-identity decision, settled under ownership `Precondition` by 32 with no uid test, and its detection from the patch response ([48](48-detect-patch-on-replacement-pod.md)).

**From 32:** [32's hand-back](32-spec-then-build-ownership-lifecycle.md#hand-back-notes). The pure pieces exist: `src/knarr/lifecycle.gleam` with `due`, `done`, `held` (from ownership's `read` and `standing`, an unparsable applied record a conflict) and `deployment_of` (the ReplicaSet's controller owner of kind Deployment, empty otherwise) over `View`, `Held` and `Removal`; `ownership.cleanup(marker:, annotations:, owned:, at:)` builds the `Released` patch and `ownership.left(operations:, annotations:)` names what a rejected cleanup left; `observability.rejected_message` renders the `CleanupRejected` message for one, two and no annotations left. No cleanup is sent yet: nothing builds a `View`, and the reconciler's `Cleanup` arm is compiled but never reached. The rejection hook is purpose-agnostic: `reconciler.rejection(cycle:, deployment:, pod:, memory:, operations:, purpose:, status:)` takes the deployment label as a name, `lifecycle.deployment_of`'s for a pod that is not a target, counts `knarr_patch_rejections_total{deployment, purpose}` on every call and raises the Event on the first rejection of a run per reason; call it from the cleanup's send with purpose `Cleanup`, a 400 or 403 at once and a 422 through `Kept(operations, Cleanup)` and `classify_kept(cycle:, deployment:, pod:, memory:)`, which passes the kept purpose through; `left` is computed inside from the purpose, so nothing extra is passed. `ownership.owned_annotations` is public and `ownership.cleanup` returns no operations for a pod without an annotations map. This ticket owns the cleanup cases of 32's cadence: a 403 twice raising one `CleanupRejected` Event, an accepted patch of any purpose ending the run, and the retry under lifecycle `Retry`. The reconciler's `retain_runs` keeps the rejection runs of every live pod the unselected pod LIST still shows but the cycle did not poll, so a `cleanup_rejected` run on a pod of an opted-out Deployment lasts across cycles as observability `Cadence` `OnEntry` says, and a rejected cleanup raises `CleanupRejected` once per run, not at every cycle. The `cleanup rejected` line carries `left` as an array of `key=value`, present and empty when nothing is left. Two review findings are deferred to this ticket's pass over every listed live pod, as explicit tasks: final finding 1, a kept 422 on a pod the next cycle does not poll (its Deployment opted out, or it lost its IP) is never classified, so that rejection's counter, Event and line are lost; final finding 3, a foreign annotation on a target pod without an IP is neither announced nor gauged, and losing and regaining the IP announces twice. Both share the cause that `classify_kept`, `announce` and `gauges` see polled pods only, and the fix is the pass over every listed live pod that 47's View builder makes, classifying a kept 422 there with the deployment from `lifecycle.deployment_of` for a non-target; they were deferred to keep this ticket's reconciler diff minimal while 46 reworks the same file. Two more, from the `/code-review` pass: the rejection runs and the reading state are keyed by pod name, so a pod deleted and recreated under the same name inside one LIST interval inherits the old run and its first rejection raises no Event, low likelihood (the name window ownership `Precondition` concedes), to be closed by a uid in `Memory` ending both on a change; and the parse-forced conflict is computed in both `reconciler.view` and `lifecycle.held`, so the View builder is the place to share one effective-standing function. The pod-identity question is settled under ownership `Precondition`; 48 detects a write that landed on a replacement.

### Choices a maintainer may reverse

- Retirement candidates come from the names that carry series, not also from the names Views carry. A View holds `done` false only through an owned annotation, which `knarr_annotations` counts under the same name, so the two sets agree on everything observable; adding View names would send a no-op departure every cycle for every opted-out Deployment whose released pods still run. The reconcile `Cycle` prose says the same: a name out of the target set "that carries series".
- `knarr_annotations` for a name out of the target set is rebuilt from the Views each cycle while its other gauges hold their last values (observability `Standing` read as the more specific clause than `SeriesLife`'s "gauges at their last values").
- A replaced pod's cleanup entry and last attempt are forgotten even while it is cleaning, so the replacement's cleanup starts from its own due_since.
- The reconciler keeps a memory, its Pod and its View, for every pod the unselected pod LIST shows, marked or not, so the uid fence and the patcher's `replaced` cover every listed pod. Keeping memory only for pods with a held record, a kept 422 or a run would shrink the state in a shared namespace, at the cost of forgetting a released pod's uid.
- Retirement candidates are read off the deployment labels on the reconciler's own gauge and counter series, not from a tracked set of names. It holds today, since every name that has outstanding work also carries a reconciler series (the `retirable` comment argues each case), but a future per-Deployment metric kept outside `state.gauges` and `state.counters`, as `knarr_patches_pending` is in the patcher, would have to join that set or a tracked set of names.
